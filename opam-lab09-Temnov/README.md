## Завдання 3. Додатковий алгоритм (сортування підрахунком)

* У скільки разів швидше за алгоритм із завдання 2:
  На масиві розміром n = 1 000 000 сортування підрахунком працює у [T_злиття / T_підрахунок] разів швидше за сортування злиттям знизу вгору (наприклад, ~25–35 разів). Це досягається завдяки лінійній асимптотичній складності O(n + k) без порівнянь елементів між собою, тоді як сортування злиттям виконує O(n log n) операцій і постійно переписує дані між основним та допоміжним масивами.
* За яких умов можна застосовувати сортування підрахунком:
  1. Ключі елементів є цілими числами (або однозначно відображаються у скінченний діапазон невід'ємних цілих індексів).
  2. Розмір діапазону значень k = max - min + 1 є порівнянним із кількістю елементів n або меншим за нього (у нашому випадку k = 381). Якщо k значно більше за n (наприклад, довільні 32- або 64-бітні цілі числа), виділення масиву лічильників потребуватиме надмірної кількості пам'яті, а ітерація по ньому нівелює перевагу в швидкості.

### Пояснення отриманих чисел

1. Сортування вставками:
   * На відсортованому вході: робиться рівно n - 1 порівнянь (кожен елемент перевіряється лише з попереднім, і внутрішній цикл одразу зупиняється) та n - 1 записів у масив (запис a[j + 1] = key на кожному кроці; обмінних зсувів нуль).
   * На відсортованому навпаки: найгірший випадок — кожен новий елемент менший за всі попередні (крім дублікатів), тому кількість порівнянь та зсувів квадратична й наближається до n(n - 1) / 2.
   * На випадковому вході: елемент у середньому просувається на половину вже відсортованої частини, тому кількість операцій становить приблизно n^2 / 4.
   * На майже відсортованому вході (K = 19 обмінів): зміщено не більше 38 елементів, тому кількість порівнянь і записів зростає лінійно відносно n і лише незначно перевищує показники повністю відсортованого масиву.
2. Сортування злиттям знизу вгору:
   * Кількість записів у масив (moves) у всіх чотирьох колонках для фіксованого n однакова і становить n * ceil(log2(n)) (на кожному рівні злиття всі n елементів переписуються між основним масивом і буфером).
   * Кількість порівнянь майже однакова на всіх типах входу (приблизно n * log2(n)), оскільки алгоритм не адаптується до початкової впорядкованості, а завжди розбиває масив на блоки розміром 1, 2, 4, ... На повністю відсортованому та зворотному входах порівнянь трохи менше, бо один із підмасивів вичерпується швидше, і хвіст другого копіюється без порівнянь.
3. Сортування підрахунком:
   * У всіх 12 клітинках кількість порівнянь дорівнює 0 (алгоритм працює виключно з частотами індексів, не порівнюючи елементи між собою), а кількість записів дорівнює 2n (n записів у проміжний масив output для забезпечення стабільності та n записів назад у вхідний масив a).

## Завдання 6. Висновки

1. Відношення порівнянь простого й швидкого алгоритмів на n = 10 000 проти лекційного числа 376:
   За моїми вимірами відношення становить:
   C_вставки(10 000) / C_злиття(10 000) = [число з табл. 4] / [число з табл. 4] ≈ [результат]
   Воно відрізняється від лекційного числа 376 з двох причин: по-перше, лекційне число розраховане для теоретичної пари з іншою константою (наприклад, для вибору/обмінів або QuickSort із константою 2 * ln(2)), тоді як сортування злиттям робить менше порівнянь у середньому (приблизно n * log2(n) - 0.91n); по-друге, наш вхідний масив містить 10 000 чисел із вузького діапазону [0; 380], тому в ньому багато дублікатів (близько 26 копій кожного значення), на яких сортування вставками зупиняється раніше і робить менше порівнянь, ніж на масиві з унікальних елементів.

2. Дві причини, чому Array.Sort швидший за власний O(n log n) алгоритм (окрім «краще оптимізований»):
   * Відсутність викликів делегата на кожному порівнянні: у власній узагальненій реалізації кожне порівняння викликає переданий делегат Func<T, T, int> cmp, що створює накладні витрати на непрямий виклик функції мільйони разів. Array.Sort(int[]) використовує внутрішню реалізацію CLR, де порівняння примітивних типів виконується напряму машинними інструкціями процесора без виклику методів.
   * Локальність кешу процесора (In-place проти допоміжного масиву): Array.Sort (IntroSort) працює на місці (in-place) в межах одного масиву, максимально ефективно використовуючи кеш-лінії процесора L1/L2. Сортування злиттям на кожному проході читає дані з одного масиву й записує в інший (aux), що подвоює обсяг використовуваної пам'яті та збільшує кількість кеш-промахів.

3. Вибір алгоритму для задачі (100 000 записів, ключ 0..300, щоденне сортування, обов'язкова стабільність):
   Обираю сортування підрахунком (Counting Sort) із використанням префіксних сум та заповненням вихідного масиву справа наліво.
   Обґрунтування: діапазон ключів k = 301 дуже малий порівняно з розміром вибірки n = 100 000, тому алгоритм працюватиме за лінійний час O(n + k), що в десятки разів швидше за будь-які алгоритми на порівняннях (O(n log n)). Допоміжний масив лічильників займе лише близько 1.2 КБ оперативної пам'яті, а прохід по вхідному масиву з кінця при розставлянні елементів за префіксними сумами суворо зберігає взаємний порядок записів з однаковими ключами (стабільність).
